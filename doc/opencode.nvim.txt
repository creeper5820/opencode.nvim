1. REQUIREMENTS                                        *opencode.nvim-requirements*

- Neovim >= 0.10 (uses |vim.uv|, terminal buffers and buffer-local mappings).
- The `opencode` CLI available on `$PATH`.

The plugin starts the official CLI in a terminal buffer. It does not require a
separately started server, TypeScript package or HTTP transport.

==============================================================================
2. SETUP                                                     *opencode.nvim-setup*

>lua
  require("opencode").setup({
    cmd = "opencode",
    args = {},
    project = { root = nil },
    session = { continue = false, id = nil, prompt = nil },
    window = { layout = "right", size = 80, start_insert = true },
    keymaps = {
      toggle = "<leader>oo",
      send_selection = "<leader>os",
      question_selection = "<leader>oq",
      focus_next = "<Tab>",
    },
    keybindings = {
      enabled = true,
      cli_path = nil,
      read_cli = true,
      overrides = {},
      sequence_timeout = nil,
    },
    input = { primitives = true, passthrough = true },
    paste = { bracketed = true, ready_delay = 150, submit_delay = 30 },
    focus = { initial = "composer" },
  })
<

`cmd` may be a string or a list. The configured project directory is appended
as OpenCode's positional directory argument. `session.id` maps to `--session`,
`session.continue` maps to `--continue`, and `session.prompt` maps to
`--prompt`.

`setup()` is safe to call repeatedly. The previous terminal process,
buffer-local mappings and autocmds are replaced.

4. KEYMAPS                                                 *opencode.nvim-keymaps*

<leader>oo       Normal      Open or hide the OpenCode TUI.
<leader>os       Visual      Paste formatted selection context into the TUI
                             composer; never submits.
<leader>oq       Visual      Open a real Neovim float, then paste question +
                             context and submit it.

Set a keymap to `false` to disable it. These are global editor mappings; all
terminal input routing is buffer-local.

==============================================================================
5. TERMINAL LIFECYCLE                                    *opencode.nvim-terminal*

The TUI uses one terminal buffer and one Neovim window. Hiding the window does
not stop the process; the official TUI keeps its composer, viewport and session.
Use `:OpenCode stop` to terminate it or `:OpenCode restart` to start a fresh
process.

Per-open flags:

>lua
  require("opencode").open({
    directory = "~/src/project",
    session = "ses_123",
    continue = false,
    prompt = "Review the diff",
  })
<

When a TUI is already running, `open()` reveals it instead of silently changing
its session. Stop or restart first when changing those flags.

==============================================================================
6. INPUT ROUTING                                            *opencode.nvim-input*

Terminal Insert mode is pass-through: the TUI receives all keys. `<Esc>` keeps
its Neovim meaning and exits Insert; `<C-\><C-n>` remains available.

Normal mode installs buffer-local mappings in the OpenCode terminal buffer:

1. Effective OpenCode `cli.json` bindings, including alternatives, custom
   leaders, full multi-key sequences and modifier combinations.
2. Composer/session editing primitives.
3. The configurable logical-focus key.
4. Pass-through for otherwise unbound printable/special keys.

There is no global `on_key` hook and no screen-row inspection. `i` and `a`
enter terminal Insert mode, and `:` / `/` remain Neovim commands. `I` and `A`
fall back to Neovim when no native OpenCode binding owns them.

7. LOGICAL FOCUS                                         *opencode.nvim-focus*

The TUI renders both areas, but input routing records two logical regions:
`composer` and `session`.

>lua
  local opencode = require("opencode")
  opencode.focus_input()
  opencode.focus_session()
  opencode.focus_next()
  opencode.get_focus()       -- "composer" | "session"
  opencode.get_focus_state() -- { region, saved, active, reason, changes }
<

Focus changes only through these explicit calls, the configured focus key, or
leaving/returning to the real OpenCode window. Cursor movement, row numbers,
scrolling and `j`/`k` never switch regions. Returning to the window restores the
previous region.

`keymaps.focus_next` defaults to `<Tab>`, but it is skipped when an effective
OpenCode binding already owns that key, so native Tab/Shift-Tab behavior is
preserved. Set another key or `false` as needed.

8. PRIMITIVES                                        *opencode.nvim-primitives*

Composer primitives translate a small Vim-like vocabulary into the TUI's own
input operations: `h`, `l`, `j`, `k`, `w`, `b`, `e`, `0`, `^`, `$`, `gg`, `G`,
`x`, `X`, `D`, `C`, `u`, `<C-r>`, `<C-d>`, `<C-u>`, `<C-f>`, `<C-b>`, page keys,
`d{motion}` and `c{motion}`. Text objects, registers and macros are not
implemented.

The same primitive name dispatches by region. For example `line_down` moves the
composer cursor in the composer region and scrolls the session in the session
region. Primitives never change the logical region.

Public API:

>lua
  local opencode = require("opencode")

  opencode.primitive("page_down", 2)

  opencode.map_primitive("<C-n>", "page_down")
  opencode.map_primitive("gl", "line_down", { count = false })
  opencode.unmap_primitive("gl")
<

`map_primitive()` installs a Normal-mode mapping in the current terminal buffer
and forwards `vim.v.count1` unless `opts.count = false`.

9. KEYBINDINGS                                        *opencode.nvim-keybindings*

Resolution order:

1. OpenCode V2 TUI defaults.
2. `keybindings.cli_path`, or
   `$OPENCODE_CONFIG_DIR/cli.json` / `$XDG_CONFIG_HOME/opencode/cli.json`.
3. `keybindings.overrides` (always wins).
4. `keybindings.read_cli = false` skips the file;
   `keybindings.enabled = false` disables native Normal-mode mappings.

Both `keybinds` and `keybindings` objects are accepted. A string may contain
comma-separated alternatives; arrays, binding objects and key objects are also
accepted. `<leader>` expands to the complete configured leader sequence.

Keys that cannot be represented as terminal input are skipped with a
non-blocking diagnostic. Run `:OpenCodeHealth` to inspect them.

==============================================================================
10. SELECTION ACTIONS                                *opencode.nvim-selection*

`send_selection()` extracts the Visual selection, formats a Markdown context
block and pastes it through the terminal channel without submitting.

`question_selection()` opens an editable float. `<C-s>` pastes the question and
context as one bracketed paste, then sends a separate Enter/Submit event.
Cancellation sends nothing. Empty questions are rejected. Failure keeps the
float text when possible; a failed submit after a successful paste asks the user
to press Enter in the TUI.

Text is never interpreted as TUI shortcuts because it is sent inside a
bracketed paste. Multiline paste and submit are separate writes. OpenCode owns
all session state.

==============================================================================
11. HEALTH                                                  *opencode.nvim-health*

`:checkhealth opencode` and `:OpenCodeHealth` report:

- Neovim and |vim.uv| availability;
- configuration validity;
- the OpenCode executable and `--version`;
- terminal process/window state;
- effective `cli.json` and keybinding diagnostics.

No network service is required.

==============================================================================
12. TESTING                                              *opencode.nvim-testing*

Run tests only through the isolated runner:

>sh
  bash tests/run.sh
  bash tests/run.sh tests/unit/router
<

The runner creates temporary HOME, XDG config/data/state/cache, runtime, shada
and project directories under `/tmp/opencode`. The terminal smoke test starts
an isolated official OpenCode TUI with `--standalone`, verifies output and PTY input, then
stops only its own process. It never connects to the user's OpenCode service or
configuration.

==============================================================================
13. LIMITATIONS                                      *opencode.nvim-limitations*

- One embedded TUI per Neovim instance.
- Logical focus is an input-routing abstraction; OpenCode renders both regions
  in one terminal.
- TUI dialogs, permissions, session selection and completion belong to
  OpenCode.
- Modified-key support depends on the terminal and OpenCode input protocol.
- Selection submission does not wait for agent completion.
